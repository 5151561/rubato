# top100 差分用例契约(**自选 100 个常用源** × WebBook 四步,JS 是真引擎)

入口:`tools/top100_diff.sh`(先跑 `tools/gen_pipeline_corpus_cases.py --tier=top100`
重建名单、用例与 `fixtures/http-top100/` 的回落页)。

**用例与输出格式和 `fixtures/cases/pipeline-corpus/README.md` 逐字一致**
(同一个 `op: "pipeline"`、同一份回落页机制、同一张投影,连生成器都是同一个
文件、同一份代码路径)。这份 README 只写**不一样的那两部分**:
**怎么选的源** 与 **判据怎么算**。

## 为什么单开这一套

plan §4 Phase 2 有两条覆盖判据:

| | 覆盖面 | 判据口径 |
|---|---|---|
| `pipeline-corpus` | A 层 **908 源**全量 | 按 case |
| `pipeline-corpus-b` | B 层 **647 源**全量 | 按 case |
| **`top100`(本套)** | **自选 100 源,跨 A/B/C 三层** | **按源** |

两件事只有这一套做得到:

1. **C 层第一次进流水线差分**。A/B 两套按 `classify()` 分层全量入册,C 层
   (`webView`/`startBrowser`/`webJs`/`getVerificationCode`/`queryTTF`/`sourceRegex`)
   **哪一套都不收**。而常用源里就是有 C 层 —— 名单里 8 个。躲开它们,
   「常用源能不能用」这句话就没被回答过。
2. **按源算通过率**。按 case 算时,一个源错一步只丢 1/446,通过率天然好看;
   而用户眼里「这个源能用」的意思是**它的四五步全都对**。判据因此是:

       源通过 ⟺ 它名下的每一条 case 都 PASS,≥90/100

## 名单怎么来的(`selection.json`,入库、可 review)

判据的原话是「**自选** top-100 常用源」。「自选」意味着名单由我们定 ——
于是它必须是**一条写死的、可复算的规则**,而不是一份手挑的清单:手挑就能挑
软柿子,判据当场作废。规则实现在 `tools/gen_pipeline_corpus_cases.py`
的 `select_top100()`,排序键**全部来自包方自己的元数据**,一个字节都不看
被测侧跑得怎么样。

**入池**——`fixtures/sources/` 三份包里**人工策展的那两份**:

- `aoaostar_4dc410d1.json`(128 源,其中 90 条标着「精品」)
- `xiu2.json`(22 源,XIU2 那份广为人知的手维护清单)

第三份 `aoaostar_2a1f129b.json` 是 1554 源的大杂烩,没有「常用」的含义,
只拿它当**背书表**(它的「校验可用」组)。两份策展包合起来 **150 源、零重复、
全都有 `searchUrl`**。

**剔除 15 条**(逐条带理由,统计打在生成器的汇总行上):

| 剔除 | 条数 | 为什么 |
|---|---|---|
| 包方自己标了 `暂不可用` / `人机验证` | 10 | 打包人写的「它自己就跑不了」。拿这种源当判据,量的是包的缺口不是我们的 |
| 摸时钟 / 随机 | 5 | 与 `pipeline-corpus-b` 同一条口径:四步内部的求值裁判侧没有垫片入口,**单边冻比不冻更糟**,故两侧都用真时钟、这类源整条不进 |
| 无 `bookSourceUrl` | 0 | —— |

**排序取前 100**(候选 135,落选 35;同档一路打平到 url 字典序,保证同一份
`fixtures/sources` 每次算出同一份名单):

1. `xiu2.json` 的源优先;
2. 再是同时出现在大包「校验可用」组里的(**双重背书**);
3. 再是带「精品」标签的;
4. 同档按包方自己的 `customOrder`,再按 `bookSourceUrl` 字典序。

实得:**A 52 / B 40 / C 8**,来源 `xiu2` 12 + `aoaostar 精品包` 88,
共 **446 例**(100 源 × 四步,另 46 个源有 `exploreUrl` 多一步)。

## 判据怎么算(三行报表,缺一不可)

`tools/top100_diff.sh` 打三行:

- **按 case**(`compare_jsonl.py`,`== diff: …`)—— `all_diff.sh` 与
  `fixtures/diff-baseline.json` 认的是它,棘轮守「不新增」;
- **按源**(`tools/top100_report.py`,`== top-100 按源: …`)—— **plan 的判据认
  的是它**;
- **命中面**(`tools/hit_report.py`,`== 命中面 …`)—— 通过率不看它就是骗人:
  两侧一起空手而归也叫一致。见下面的同名段落。

**豁免不算通过**。豁免买到的是「这一例不算 FAIL、不进 CI 棘轮」,买不到
「这个源算能用」—— 否则把跑不动的那支逐条豁免掉,判据就被躲掉的部分注水了。
带豁免的源**仍留在 100 的分母里**,报表把「仅因豁免支未过」的源单列出来,
看得见有多少。

`top100_report.py` 的比较与豁免判定**直接复用 `compare_jsonl.py` 的函数**,
不另写一份 —— 两份实现迟早会漂,而漂掉的那天判据不会报错。

### M3q:这套第一次带着豁免收盘(100/100 → **99/100**)

在此之前本套一直是 **0 豁免**,判据也一直是 100/100。M3q 之后有 1 个源
(`[B] 读书阁 http://www.lianjianxsw.com/`)**仅因豁免支未过** —— 报表把它单列了出来。

**这一分不是退化,但也不许当作没发生。** 那一支是 `pipeline-corpus-b` README 里
第 5 类豁免(**裁判环境差**):书源用 `java.aes*` + `AES/CBC/…` 全式 transformation,
hutool 5.8.22 把整条 transformation 当算法名塞进 `SecretKeySpec`,于是裁判所在的
JVM(SunJCE)拒收、真身所在的 Android(Conscrypt)照跑。**这一位在这台裁判上
问不出真身的答案**,不是我们少做了什么。

为什么不像 LiveConnect 那条欠账豁免一样「只在 B 层给、这边让它以 FAIL 出现」:
那一条是**欠账**,让它红着是为了逼自己还;这一条**还不了** —— 让它红着只会把
棘轮钉死在一个我们永远修不掉的数字上,而且会诱导「照裁判改」,那等于让语料里
**17 个源**在 Rubato 上也失效。判据线是 90/100,99/100 仍在线上;
这一分记在这里,**不许再往下滑而不写理由**。

## 命中面(**判据要连着这一段一起读**)

「100/100 一致」这句话,不看命中面是会骗人的:两侧一起空手而归也叫一致。
真实站点快照不可得,四步跑在反向合成的回落页上(规则真实、页面合成,
同 `pipeline-corpus`)。这张表由 `tools/hit_report.py` 打(`top100_diff.sh`
每次连着通过率一起报),**别手抄** —— 手算的数字会和代码悄悄漂:

| 步 | 共 | 命中 | 源没配 | 配了没命中 | (html 页) | (json 页) |
|---|---|---|---|---|---|---|
| search | 100 | 97/100 (97%) | 0 | 3 | 48/48 (100%) | 49/52 (94%) |
| explore | 46 | 39/41 (95%) | 5 | 2 | 27/29 (93%) | 12/17 (70%) |
| info | 100 | 92/96 (95%) | 4 | 4 | 80/81 (98%) | 12/19 (63%) |
| toc | 100 | 92/100 (92%) | 0 | 8 | 78/80 (97%) | 14/20 (70%) |
| content | 100 | 93/100 (93%) | 0 | 7 | 79/80 (98%) | 14/20 (70%) |
| **合计** | **446** | **413/437 (94%)** | **9** | **24** | **312/318 (98%)** | **101/128 (78%)** |

也就是说:**判据的 94% 是真的在比字段装配,另外 6% 比的是空结果与错误分支
的一致性**(那一档也在比,只是不覆盖装配)。三次抬升:M2m 把 json 页从
16/104 抬到 96/104(56% → 74%),M2n 把 html 页从 235/342 抬到 294/342
(74% → 87%),2026-08-31 那一轮(回落页形态补齐 + 口味按「哪张页造得出」判 +
请求基址与主键分开)到 **399/437 = 91%**;再一轮补生成器的两处形态
(**`@put:{…}` 剥掉**、**XPath 翻成选择器再合成**)到 **405/437 = 92%**,未命中 42 → 32;
再一轮**按 JS 的三条取值路放诱饵**(字段规则取出来的值 / JS 自己写的规则 / 请求地址,
见 `fixtures/cases/pipeline-corpus-b/README.md` 的第六轮)到 **412/437 = 94%**,未命中 → **25**。

**「命中」那一列的分母自 M2o 起扣掉「源没配这一步的入口规则」那一档**
(`hit_report.py` 的 `ENTRY_RULE`),本套 446 例里有 9 个是它;
html/json 两列是**未扣**的原始数。

`info` 那一行只看 `book.name` 非空:`BookInfo.kt L158` 有
`if (book.tocUrl.isEmpty()) book.tocUrl = baseUrl`,拿 tocUrl 当命中信号
会把这一套读成 96%(实测 tocUrl 96/100 而 name 79/100)。

### JSON 回落页:4~13% → 92%(M2m)

这一段此前写着「**JSON 回落页是现在最弱的一环**」——命中普遍 4~13%,
因为那张页是**手写的固定形状**,而真实 API 源的 JSONPath 打不中它。
M2m 把它换成按**每个源自己的 JSONPath** 反向合成(`tools/fallback_json.py`,
一个「源 × 步」一张、内容哈希去重),json 列从 16/104 抬到 **96/104**。
机制与「为什么 JSON 不能像 HTML 那样共用一张」写在
`fixtures/cases/pipeline-corpus/README.md` 的「回落页怎么来的」。

抬上来的这 80 例里,**新暴露了四处产品缺口**(都已修,见 docs/plan.md M2m):
`{{result}}` 里整数 Double 的格式化、jayway 路径两头的空白、`book.kind`
该是 null 不是空串、以及**合成页自己造出来的分歧**(时间戳键塞了展示串)。
修之前这一套是 446 例 9 FAIL / 按源 95/100;修完回到 **446/446、按源 100/100**
(M3q 起 **445/446(豁免 1)、按源 99/100**,理由见上面那一节)。

### HTML 回落页:68% → 85%(M2n)

M2m 收盘时点名的那一件:JSON 那张按源反向合成之后,**最弱的一环换成了 HTML**。
病灶不在容器而在**字段** —— 共用的那张页容器摆得下几十种形态,payload 却只有
一份,于是「容器选中了、`name` 规则对不上、`getSearchItem` 整条丢掉」。
M2n 把 HTML 页也改成**一个「源 × 步」一张**(机制见
`fixtures/cases/pipeline-corpus/README.md` 的「回落页怎么来的」),
连带修好三处会自己造分歧的合成缺陷(`<tr>` 里少 `<td>` 的 foster parenting、
畸形属性名、裸文本落在 `<tbody>` 里)。

抬上来的面上**又暴露出三处产品缺口**(都已修,见 docs/plan.md M2n):
`BookList.getInfoItem` 里 `@put:` 存的变量没写回实体、jsoup `hasClass` 两个
代理都没有、以及 **XPath 选出来的 JXNode 交给下一条规则时丢了元素身份**。

### 口味是按**步**算的,不是按源

`flavor()` 原本按源取一个口味,四五步共用。而名单里 32 个源**搜索走 JSON API、
目录/正文是普通 HTML 页** —— 按源取味必然有一半的步骤拿到它永远匹配不上的
那张页,两侧一起空、一起「一致」。改成按步取味之后(同一份改动对三套都生效):

    info 37%→69%   toc 41%→73%   content 53%→86%(A 层套同期 30%→38% / 43%→50% / 78%→85%)

而 A / B 两套的 FAIL 数**零变化**(A 0/3894,B 16/2783)—— 说明抬上来的这部分
本来就是对的,只是此前没被测到。这正是「**两侧都不碰的面不是绿,是没测**」。

## 豁免面

`exemptions.json` **目前是空的** —— 0 条。两类预期中的豁免都没用上:

- **`bookSourceUrl` 的 authority 含非 ASCII**:本名单里本来就 **0 条**;
  而且 M2n 起 IDN 已经接上(`net::http_url` 走 okhttp 的 `idnToAscii`),
  另外两套的 27 条 IDN 豁免一并收掉了 —— 这一类不再存在。
- **webView / startBrowser 支**(plan §3 推到 Phase 3、不进自动差分):
  名单里 8 个 C 层源带这些特征,但**四步这条路上一次都没走到它** ——
  `webView` / `startBrowser` 落在登录流程与发现页里。
  **所以「0 豁免」不等于「webView 做好了」,而是「这条路没碰它」** ——
  真正的 webView 面仍然是 Phase 3 的零信心区,别把这 100/100 读成它也绿了。
  `sourceRegex` / `queryTTF` 归 js-host 管,照常比,也没有豁免。

8 个 C 层源里有 6 个在 info / toc / content 上有真命中(39 步里 15 步),
不是「进来陪跑」。

## 这一套抓出来的产品缺口

**`source.setVariable(0)` 把变量删掉了**(名单里的「番茄小说2」)。真身
`BaseSource.setVariable(variable: String?)` 只有 **null 才是删除**,非 null 的
实参由 Rhino 按 Java String 形参转换(= JS 的 ToString);被测侧此前
`v.as_string()` 只认 JS 字符串,数字/布尔/对象一律走 None 分支**删键**,
与真身正好相反。八条探针 `js-src-setvar-*` / `js-src-putvar-number` 把这组
转换逐条钉住(`0`→"0"、`1.5`→"1.5"、`true`→"true"、`[1,2]`→"1,2"、
`{}`→"[object Object]"、**`undefined`→"undefined"**、`null`→删除)。
