# 书源引擎逐例计时:被测(Rust)vs 裁判(legado 真身)

> 数据由 `tools/time_diff.sh` 产出,2026-09-01 在 macOS(darwin 27.0.0)上跑的十八套、
> 101129 例。表可以随时重跑,**别手抄**(docs/plan.md 首页那个「92119 例」就是手加飘掉的)。
>
> 本文有**四轮**数:第一轮是接上计时后的原始状态,第二轮修掉 §3 ①②④,
> 第三轮修掉 ③,第四轮修掉 ②里「躲不掉」判错的那一半(固定脚本的字节码缓存)。
> 正文里的表是**第四轮**;各轮对照在 §6。

## 一句话结论

**没有单一的「快多少倍」。** 按套的逐例倍数中位数是 **1.3×**,但十八套加起来的
总耗时被测侧仍是裁判的 **1.25 倍**(裁判 6.62s / 被测 8.30s)—— 差距全在几条
可指名的真因上,不是「Rust 比 Kotlin 快/慢」这种句子能概括的。

谁要一个数,就给这两个,并且必须一起给:

| 口径 | 数 | 它的意思 |
| --- | --- | --- |
| 逐例倍数按套取中位数 | **1.3×** | 一条**典型**规则,被测侧略快 |
| 十八套总耗时比 | **0.8×**(慢 1.25 倍) | 把最慢那批算进去,被测侧仍输 |

两个都是真的。分歧本身就是结论:**赢在窄面上,输在几个热点上**。
剩下的 1.68s 差距里 1.5s 在 `pipeline_corpus_b` 一套,真因单一
(每次 evalJS 约 205µs 的固定开销 × 每例多次求值),下一步是谁也写在 §3② 末尾。

## 0. 这份数怎么来的

不另建 benchmark —— 两侧已经在同一份 fixture、同一批 HTTP 快照上跑同样的用例,
分母是现成的,而且是**被判过一致**的。自己另写一份 benchmark 只会量到两段不同的代码。

- 两侧的执行器在 `RUBATO_DIFF_TIME=1` 下给每条输出补一个旁路字段 `__ns`
  (`difftest::run_jsonl` 与 `judge/{harness,jsharness,wvharness}` 三个 `Main.kt`);
- `compare_jsonl.py` 比较时摘掉 `__ns` —— 计时**不进判据面**,十八套仍是 0 FAIL;
- 关掉时是老路径逐字节等价,CI 不受影响。

三件必须做对的事,做错了数就是假的:

1. **Rust 走 release**(`RUBATO_DIFF_PROFILE=release`)。debug 在正则/解析这类活上
   慢一个量级,拿它去和 JIT 热了的 JVM 比是自己给自己抹黑。
2. **JVM 要预热**(`RUBATO_DIFF_ROUNDS`,缺省 3,**逐例取最小**)。第一轮跑在解释器里,
   不预热量到的是「JIT 没热」而不是「Kotlin 慢」。两侧同一条规则,免得口径分岔。
3. **FAIL 数不能变**。多轮重跑若有状态残留(cookie、已定义的 doc),最后一轮的输出会和
   单轮不同 —— `time_diff.sh` 逐套对 `fixtures/diff-baseline.json` 核一遍,变了就把那套
   踢出报表。两轮全量各十八套都与基线一致。

还有一处口径细节:裁判侧的计时取在**工作线程内部**(`AtomicLong` 回传),不含
`executor.submit`/`future.get` 那次交接。最快的几套单例只有一两微秒,把几十微秒的
线程交接算进去等于给裁判侧灌水。

`倍数 = 裁判耗时 / 被测耗时`,大于 1 是被测更快。「总耗时比」被最慢的那几例主导,
**不能当成「快多少倍」** —— 逐例倍数的 p50 才是典型值,两列一起看才看得出形状。

### 哪一列可信 —— 这条是量出来的,不是猜的

**两侧的分布挨得近时,`倍数 p50` 与「被测更慢」的条数会在噪声里翻。**

- `url` 套一个字都没改,连跑三次是 0.8× / 0.9× / 1.3×(实测)。
- `html` 套在同一份代码上,`倍数 p50` 在 0.9× 与 1.2× 之间摆、「被测更慢」在
  2090 与 14887 之间摆 —— 而两侧的**总耗时**三次复跑稳定在 ±1%。

原因:这两套的单例只有 1~10µs,两侧的分布几乎重合,`ratio < 1` 这个判定对
几百纳秒的抖动极其敏感。**微秒量级的套只看总耗时**,别看 p50 的小数位、
更别把「被测更慢 N 例」当结论 —— §3③ 里我第一次就是拿这个数下的判断,错了一半。

**总耗时是可信的**:裁判侧代码四轮没动过,它的十八套合计是
6.74 / 6.78 / 6.71 / 6.62 秒,逐套也基本不动(只有 `rule` 摆了 16%)。那就是本机的噪声底。

## 2. 赢在哪

- **analyze_url 4.3×、charset 3.6×**:纯计算、无外部引擎、无大对象的面。p10/p90 收得很窄
  (3.7/5.2),说明是**结构性**的快,不是某几条撑出来的。
- **regex 3.3×**:第一轮它是全套最输的一条(0.1×),编译缓存之后反过来了 —— 见 §3①。
- **syntax 2.2×、pipeline 2.0×、json 1.5×**:短输入上的解析,典型规则都在这一档。
- **webview 18.2×**:两侧都挂虚拟时钟,量的是**策略层记账**,不含真的等 900ms ——
  这个数好看但没有产品含义,别拿出去讲。

## 3. 输在哪 —— 真因都可指名

### ① regex:每例多花 ~40µs,是**编译**不是匹配 —— 已修

第一轮:`replaceRegex` p50 0.05×、`regexFind` p50 0.06×,8042 例里 7753 例更慢。
花的是 `JavaRegex::compile`,不是匹配 —— 两组分桶把这件事钉死:

| pattern 长度 | 被测 p50 | 裁判 p50 | | data 长度 | 被测 p50 | 裁判 p50 |
| --- | --- | --- | --- | --- | --- | --- |
| < 16 | 32.8µs | 1.42µs | | < 16 | 36.7µs | 1.25µs |
| 16–32 | 44.0µs | 1.88µs | | 16–64 | 42.2µs | 1.54µs |
| 32–64 | 55.9µs | 2.58µs | | 64–256 | 44.9µs | 2.10µs |
| 64–128 | 89.3µs | 4.79µs | | | | |
| 128+ | 115.0µs | 5.83µs | | | | |

**耗时跟着 pattern 长度走(32.8 → 115µs),几乎不跟 data 长度走(36.7 → 44.9µs)。**
单例佐证:`r06077` 的 data 只有 19 字符,仍花 637µs(裁判 2.1µs)。
`fancy-regex` 建程序的成本比 `Pattern.compile` 高一到两个量级,而两侧都是
**每次调用现编译、不缓存**。

**已修**(`regex-compat`):`JavaRegex` 改成 `Arc<Compiled>` 句柄,按
`(java 原串, 是否整串匹配)` 缓存;命中时连 `translate` 都不跑。公开 API 没动。
两条口径写在代码里 —— 只缓存**成功**的(缓存 `Err` 要让错误串可克隆,不值当);
满 1024 **整张清空、不做 LRU**(书源换源时 pattern 是整批换的;真要 LRU 得先有
一份能证明它更好的数据)。共享安全:`fancy_regex::Regex` 匹配走 `&self`,状态在
调用方的 `Captures` 上,与 Java 那个**有状态**的 `Matcher` 不同。

**结果:p50 41.8µs → 417ns,0.1× → 3.3×;被测更慢的例 7753 → 1809。**
剩下那 1809 例是**冷编译**(每个 pattern 的第一次),单条最差仍是 700µs 量级 ——
差分每套一个新进程,缓存从零开始;产品里同一条正则会被反复调用,冷的那一次摊得掉。

### ② js:一次求值 1.2ms —— 两轮修到 205µs,剩下的才真卡在执行闸上

`js` 套第一轮 p50 0.1×(裁判 128µs / 被测 1.2ms),`pipeline_corpus_b` 0.3× 是同一个因。
先把一次求值的 912µs 拆开量了一遍(临时探针,量完撤掉):

| 段 | 耗时 |
| --- | --- |
| `install_live_connect` | **369µs** |
| `JAVA_PROXY` eval | 350µs |
| `PRELUDE` eval | 70µs |
| 装箱包装器 eval | 69µs |
| `Runtime` + `Context` | 64µs |
| 宿主函数注册 | 26µs |

即 `docs/plan.md`「留着没做」那条的实测版:**Runtime+Context 只占一小块,其余都是
每次重装那三十来 KB 的 JS 面**。

**已修的那一半**(`js-host/live_connect.rs`):`Packages` / `android` / `JavaImporter`
三个名字改成懒 getter,第一次被碰才装那 12 个宿主函数与 8 KB 类面。绝大多数书源
根本不碰它们,这四成是白付的。顺带把装箱包装器的源码串 `LazyLock` 掉(3.7µs/次,
不多但纯白付)。**语义没动**:每次求值仍是全新 Context、全新 LiveConnect 实例,
只是「什么时候装」变了。

**结果:1.2ms → 744.6µs(−38%);`pipeline_corpus_b` 0.3× → 0.5×,
`pipeline_corpus` 0.7× → 0.9×,`top100` 0.7× → 1.0×。**

**第四轮把「躲不掉」这句判错的修掉了 —— 字节码缓存不必动 Runtime。**
上一轮写的是「QuickJS 的字节码绑在 `Runtime` 上」,那只对**活的** JSValue 成立;
**序列化**形态(`JS_WriteObject`/`JS_ReadObject`,qjsc 的那条路)把 atom 写成字符串、
读入时在目标 Runtime 重新驻留,**跨 Runtime 是它的设计用途**。于是
(`js-host/bytecode.rs`):JAVA_PROXY / PRELUDE / 装箱包装器 / LAZY_SHIM /
LIVE_CONNECT_JS / determinism 六段**固定**脚本进程内编译一次,之后每个新 Context
只「反序列化 + 执行」,解析整个跳过。**语义没动**:仍是每次求值全新
Runtime/Context、脚本仍逐次执行,内存/中断闸照常;编译 flags(GLOBAL+STRICT)
与原来的 `ctx.eval` 逐位相同,连异常栈里的 filename 都保持 `eval_script`。

**结果:`js` 套 p50 747.7µs → 287.8µs,被测总耗时 1779ms → 702ms(−61%);
`pipeline_corpus_b` 5722ms → 3569ms(−38%),`top100` 416ms → 235ms(−44%)。
一次 `eval_js("1+1")` 的纯固定开销实测(release,预热后)从 ~550µs 降到 205µs。**
修后再探一遍,剩下 205µs 的分布:JAVA_PROXY **执行** 76µs(建 ~40 个闭包与
原型面,不再是解析)、装箱包装器执行 30µs、PRELUDE 22µs、宿主函数注册 22µs、
Runtime+Context ~50µs、LAZY_SHIM 9µs —— 全是「每次新 Context 里重建对象」的钱。

**还没修的只剩一条,理由仍是「先钉语义,再谈性能」:**

- `SharedJsScope` / 复用 Context:真身 `getShareScope` 在同一段 JS 被调用超过
  16 次后复用 topScope,被测侧每次全新 Context。复用能把上面那 205µs 几乎清零
  (`pipeline_corpus_b` 剩的 1.5s 差距就是它),但那正好改掉**跨次求值的全局
  可见性**,还把 256 MB 内存闸从「每次求值」变成「累计」—— 是动执行闸的口径。
  这一条从 Phase 2 就记在 `docs/plan.md` 上,顺序不变。

### ③ html:两个因叠在一起 —— 已修

第一轮:`jsoupDsl` 总耗时比 0.93×、`cssSelect` **0.32×**,「被测更慢」16025 例是全表最多。
51 KB 的 `wiki` 文档上一次 `.listmain dd a` 要 3.1ms,裁判 48µs —— **65 倍**。

**先说一条我第一轮判错的**:当时拿「16025 例更慢」当主要证据,说是「普遍略慢」。
那个数一半是噪声(见 §1「哪一列可信」)。真正的证据是**总耗时**与**尾巴**,
而它们指的是两个互相独立的因。

**因一:`And` 的求值顺序反了(选择面)。** `.panel-body tbody tr` 解析成
`And([Ancestor(...), Tag(tr)])` —— **祖先条件排在前面**。而 `select` 对树里**每个节点**
调一次 `matches`,于是每个节点都要先爬一遍祖先链,链里那个 `inner` 自己又可能是
一条 `Ancestor` → 每节点 O(深度^层数)。裁判(jsoup)是先拿最右那个简单选择器
把 99% 的节点当场刷掉。

**已修**(`select.rs`):把最右那个 `new_eval` 放到组合子前面。这些匹配器都是
**纯谓词**、`And` 是 `.all()`,换序不改结果,只改代价。三行。

**因二:最内层每个节点分配一个 String + 上百次字符串比较(提取面)。**

- `dom::normal_name()` 回 `String`,每次 `to_ascii_lowercase()` 分配一个 —— 而
  html5ever 解析 HTML 时标签名**本来就是小写的**(只有 SVG/MathML 的调整名带大写)。
  这个函数在选择器匹配与文本走查的最内层,每节点至少一次。**已修**:回 `Cow`,
  绝大多数调用一个字节都不用抄。
- `tags::tag_flags()` 每次对五个 `&[&str]` 各做一遍线性 `contains` —— 一个节点上百次
  字符串比较。**已修**:进程内建一次 `HashMap`(键取五张表的并集;不在并集里的
  就是「解析期新建的未知标签」那一档,结论是个常量)。补了一条测试断言**查表与
  逐张表现算逐位一致** —— 那是这张缓存表唯一的正当性。

**结果:`cssSelect` 总耗时比 0.32× → 1.14×,`html` 套被测侧 261ms → 207ms;
最差例从 0.01×(3.1ms vs 48µs)抬到 0.23×。** `jsoupDsl` 基本没动
(0.93× → 0.95×):它 20012 例的分母压着,每例 9µs 上下,两侧本来就在同一档。

**还剩的两处,都是合成最坏形状,没继续磨:**

- `sn-deep`(32 层嵌套 `div` 的探针,363 字节)上 `*` + `outerHtml` 是 0.23×:
  选中 32 个元素、每个序列化自己的整棵子树 = O(深度²),两侧都付,但我们每个标签
  比 jsoup 慢约 4 倍。
- `wiki` 上 `*` / `div` + `text` 是 0.37×:同一个形状(选中大量元素再逐个取文本)。
  `text::text` 的走查里 `flags()` 每节点被调两三次,还能省,但收益递减。

真实书源规则(`.listmain dd a`、`[property=og:novel:author]` 这一族)已经不在尾巴里了。

### ④ syntax:长规则上两处 —— 已修(而且第一处判断错了)

整套 2.2×,但第一轮按 data 长度分桶是这样:

| data 长度 | 裁判 p50 | 被测 p50 | 倍数 |
| --- | --- | --- | --- |
| < 64 | 1.5µs | 0.7µs | 2.18× |
| 64–256 | 1.9µs | 1.2µs | 1.62× |
| 256–1024 | 3.2µs | 2.8µs | 0.98× |
| 1024–4096 | 6.9µs | 8.7µs | 0.66× |
| 4096+ | 21.9µs | 42.0µs | 0.60× |

最差的一批是同一个形状:`trim=true` + `sep=['@']` 的长 `exploreUrl`。111749 字符时
裁判 13.1µs、被测 323.9µs(**25 倍**),而且比值从 31k 到 111k **恒定在 0.04×** ——
是常数因子,不是复杂度爆炸。

**第一处判断错了,留在这里当记录。** 先怀疑的是切子串:老写法
`queue[from..to].iter().collect()` 逐 char 重新 UTF-8 编码,而裁判那边
`String.substring` 一次 arraycopy 就完(实测 7.8 字符/ns,正好是 memcpy 的速度)。
改成存字节偏移表 + 一次切片 —— **只快了 12%**。

**第二处才是大头。** `index_of` 原来是
`(from..=len-n).find(|i| queue[i..i+n] == *needle)` —— **每个位置**做一次 slice 相等
比较,单字符分隔符(`@`,书源里绝大多数)也照做。105280 字符的规则上单这一句
就是 150µs,而裁判的 `String.indexOf` 是条向量化紧循环、整例才 10µs。拆成两支:
单字符走 `position`,多字符先按首字符筛再比其余。

**结果:那条 105280 字符的规则 310µs → 171µs;整套「被测更慢」2441 → 1176,
最差例 0.04× → 0.10×(25 倍变 10 倍),p10 从 1.1 抬到 1.4。**

**还剩的 10 倍在 `RuleAnalyzer::new`**:它要物化 `Vec<char>` 与偏移表两张表,
105k 字符约 850 KB,是内存带宽下界;裁判那边 Kotlin String 本来就是 `char[]`,
零前置成本。再往下就得放弃 `Vec<char>`、改成**在字节上搜 + 二分回查字符下标** ——
那会拆掉这个文件与裁判的**逐行对应**,而整个 crate 的可信度建在那上面。
没做,记在这里。

## 4. 这个数**不是**什么

判据会骗人,这份报表也会。五条:

1. **不是端到端。** 网络是录放的(`docs/http-snapshot.md`),量到的是**纯规则求值**。
   用户感知的「快」多半在 IO 那头 —— 拿这张表去讲「打开书快多少」是错的。
2. **不是「legado 在手机上的表现」。** 裁判是 JVM + JIT 热身三轮,产品跑在 Android
   ART 上、冷启、内存受限。这里量的是**同一份算法在同一台机器上的相对成本**。
3. **裁判侧挂着 shims。** `ACacheShim` 之类是内存垫片,冷算口径与真身不同;
   webview 那套两侧都是虚拟时钟。
4. **只比输出一致的例。** 输出不一致意味着两边干的活不是同一件(一侧早早报错、
   另一侧跑完全程),那种比值没有意义 —— 91 例因此不进分母。
5. **微秒级的套读不出 `倍数 p50`,也读不出「被测更慢 N 例」。** 见 §1「哪一列可信」:
   `url` 与 `html` 不改一行代码就能让这两列大幅摆动,而总耗时纹丝不动。

## 5. 怎么复现

```
tools/time_diff.sh                       # 十八套,3 轮,release
tools/time_diff.sh --only=regex,js --rounds=5
tools/time_diff.sh --json=/tmp/time.json # 机器可读的一份
```

单套手跑也行,两个变量自己带:

```
RUBATO_DIFF_TIME=1 RUBATO_DIFF_ROUNDS=3 RUBATO_DIFF_PROFILE=release tools/regex_diff.sh
python3 tools/time_report.py regex $TMPDIR/rubato-diff-regex-compat/{judge,rust}.jsonl
```

`run` 任务的环境变量由三个 `build.gradle.kts` 显式转发 —— Gradle 守护进程是跨次复用的,
shell 里现设的变量不会自己传进 JavaExec,不转发就**静默量不到**(计时全变成没有 `__ns`)。

## 6. 四轮对照

改了六处:`regex-compat` 的编译缓存、`js-host` 的 LiveConnect 懒装(r2)与
固定脚本字节码缓存(r4)、`rule-syntax` 的 `index_of` 分支 + 字节偏移切片、
`html-compat` 的 `And` 求值顺序 + `normal_name`/`tag_flags` 去分配。
**判据面一位没动**:四轮各十八套 101129 例都是 0 FAIL,与
`fixtures/diff-baseline.json` 逐套核过。

**看被测侧的绝对总耗时,不看倍数** —— 裁判侧代码没改过,它四轮的合计
